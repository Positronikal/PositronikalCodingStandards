# Code Review Notes — PositronikalCodingStandards

## What failure looks like here

The main risk is the checker scanning its own test fixtures as real
source — regex literals in test files can match sensitive-data or
formatting checks and generate false positives that hide real findings.

## Key invariants the reviewer should check

- `positronikal-check` binary is the authoritative interface;
  `positronikal_standards_check/` Python module is the legacy
  implementation — both must agree on check IDs and pass/fail verdicts
- Check IDs must remain stable across versions (repos embed them in CI
  configs and health reports)
- `repo-template/` must stay consistent with what positronikal-check
  enforces — template and checker diverging is the most common regression
- Any new check added to the checker must also be reflected in `repo-template/`

## Paths to skip

- `var/` — health reports, not source
- `positronikal_standards_check/__pycache__/` — generated bytecode
- `.venv/` — virtual environment
- `.ruff_cache/` — linting cache
- `ref/` — read-only reference documents, not project source

## Finding standards

- Every finding must cite a specific file and line number
- Cap nits at 3 per review pass; flag the class, not every instance
- False positives in the checker itself outrank style issues in standards docs
